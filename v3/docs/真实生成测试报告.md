## 发现的缺陷

### 中危：novel 模式 UI 无法对同一章连续重roll（场景 2 发现）

- 现象：`CommandBar` 仅在最后一章候选数 =1 时显示「🎲 换一支」（`swipe-btn`）；第 2 支候选生成后按钮被 ◀▶ 候选切换器取代，`handleToggleSwipe` 在 `swipes.length > 1` 时只做 `updateSwipe` 切换、不再走 `swipeRegenerate`。
- 影响：UI 路径最多产生 2 支候选；`MAX_SWIPES=20` 的多候选能力实际不可达（A/B/C 三个视图均无其他重roll入口，已 grep 证实）。
- 测试处置：第 1 次 UI 真实重roll（swipes 1→2），第 2/3 次按前端 `appendSwipe` 语义经 PATCH 幂等 upsert 模拟（同 targetId 整行替换），数据面候选累加 4/4、swipeId 指向最新均正确。
- 建议：候选未满时保留一个「再加一支」入口（如 ▶ 切到最后一支再点一次即重生成），或长按/右键 🎲 直接重生成。

### 低危：chat 回复带他人名前缀（场景 5 发现）

- 现象：妹妹的回复正文开头出现「`哥哥: 走廊里的空气…`」文本前缀（模型模仿对话格式）；`presentable(raw, speakerName)` 内置卫生层只剥当前发言者自己的名字前缀，不剥他人名前缀，气泡显示为「妹妹： 哥哥: …」双重前缀。
- 建议：卫生层对成员表内所有名字的 `名字[:：]` 行首前缀做剥离（`ChatMember` 列表在 finalize 时可用）。

### 观察项（非缺陷）

1. **长档字数遵循不稳定**（场景 5）：3 轮连续时 1519/1801/1693 全达标；但预跑中短上下文首轮出现过 345 字（要求 800-1500）。末尾长度 hint 的遵循度随上下文长度波动，属模型行为，`appendReplyLengthHint` 机制本身工作正常。
2. **llmPrefs 的 persist version 敏感**（场景 4 踩坑）：手动向 localStorage 注入 `v3-llm-prefs` 时 version 写 0 会被 migrate 静默重置回默认（maxContext 1M），导致首次未触发摘要（该次行为按 1M 预算语义完全正确：51 条全保留、无需摘要）。UI 正常写入 version=3 无此问题，仅影响外部脚本注入方式。

## 消耗估算说明

- prompt：取每条入库消息 `extra.tokenCount`（组装层 `/api/tokenize` 实测值，含设定块/守卫/长度 hint/历史）；旁路调用（滚动摘要、风格分析）按调用参数估算。
- completion：对最终入库正文（含 swipe 全候选）调 `/api/tokenize` 计数（本地启发式，与 MiniMax 实际计费存在近似偏差）。
- 分项：场景 1≈10387、场景 2≈15856、场景 3≈23350、场景 4≈36600、场景 5≈14534、场景 6≈1390、场景 7≈3269、场景 8≈3529，合计 ≈108915。
- 超预算 9% 的主因：① 场景 4 首跑因 persist version 踩坑按 1M 预算全量注入生成了对照章（21857 prompt，属诊断成本）；② 场景 3 绑定 Sudachi 预设后 prompt 达 18725（预设体积所致）；③ 场景 2 的 4 支候选正文（12424 completion）为断言必需。
