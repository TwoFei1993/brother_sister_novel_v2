# 短剧生成功能设计共识（grill-me 评审产出）

> 2026-11-07 / 基于 v3 代码库现状逐题拷问后的共识记录。
> 依据资料：`短剧生成资料/`（AI 漫剧实操课 7 课流程图：找剧本与审剧本 → 做角色 → 做场景 → 做分镜四宫格 → 生视频 → 修镜头）。
> 实现细节以本文档为唯一起点。状态：**共识已定稿，实施未开始**。

## 一、现状盘点（代码库探查结论）

| 现状事实 | 对短剧方案的影响 |
| --- | --- |
| v3 = client(React 19 + Vite) + server(Express 薄代理) + shared(zod strict) | 数据结构与校验体系直接复用 |
| `WorkModeSchema = z.enum(['novel','chat'])`，新建后锁定不可切换（`shared/src/work.ts`） | 加第三种 `'duanju'`，锁定语义沿用 |
| 桌面新建 = `features/bookshelf/NewWorkDialog.tsx`（模式双卡片+题材+绑定）；移动端 = `MobileBookshelf.tsx` 内嵌简化新建（mode 固定 `'novel'`） | 两处新建入口都要加短剧选项 |
| planner 聊天向导一键开书固定 `mode:'novel'` | planner 一期不动，短剧剧本对话在工作台内做 |
| LLM 三通道（OpenAI 兼容/Gemini/Claude 原生）**纯文本**；默认 MiniMax 通道（M3.1-Flash） | 文本环节全复用；生图是全新链路 |
| server `services/llm.ts` 无状态薄代理，上游空闲超时 120s / 总时长 600s，错误分类码（§9.1） | 生图代理沿用同样的薄代理+错误翻译风格 |
| 全项目**无任何图像/视频生成能力** | 生图链路（含图片转存、文件上传）为纯新增 |
| secrets.json 明文存 key（对外只回掩码） | 生图 key 沿用 secrets 体系 |
| 存储 = JSON/JSONL 文件（dataDir）；鉴权 = 单密码 + HMAC cookie | 短剧数据落 dataDir，单用户鉴权沿用 |
| MiniMax image-01：`api.minimaxi.com/v1/image_generation`，同步返回**临时 URL**，支持 aspect_ratio/n/seed；官方文档确认支持「单张人物参考图保持人物特征」 | 生成后必须立即下载转存；角色一致性可走参考图（待国内端点验证） |
| 即梦（Seedance）**无公开 API**，web 版每日送积分 | 视频环节只能「导出提示词+图片 → 手动去即梦」 |
| 免费视频网站调研：PixVerse/可灵/Vidu/海螺均有每日免费积分，但全部网页手动、无免费 API；开源 Wan2.1 需本地 GPU | 结论：即梦导出路径是唯一现实路径 |

## 二、已确认的决策（逐题结论）

### D1 链路终点：文本 + MiniMax 生图，视频导出即梦
- 剧本/拆解/角色档案/场景档案/分镜脚本 = 现有文本 LLM 通道。
- 角色设定图/场景图/镜头四宫格 = MiniMax image-01；返回 URL 由 **server 立即下载转存** `dataDir/works/{id}/duanju/images/`（临时链接不可依赖）。
- 生视频 = App 导出提示词+图片 → 一键跳转即梦 web 手动图生视频。一期不接任何视频 API。

### D2 入口形态：第三种作品模式
- `WorkMode` 增加 `'duanju'`；新建弹窗模式区变三选卡片（小说默认 / 对话写作 / 短剧），创建后同样锁定。
- 书架、分组（shelfTag）、题材主题、统计体系复用；书架卡加模式标识（短剧 badge）。
- 短剧内部数据（剧本/角色/场景/集/镜头）与小说的章节消息流**完全隔离**，存独立结构（见三）。
- 移动端新建弹窗同步加短剧选项（现固定 novel）。
- planner 向导一期不动（只开小说）；短剧的剧本 AI 对话在工作台剧本 tab 内实现。

### D3 工作台形态：分区 tab + 依赖提醒
- 短剧作品页 = tab 面板：**剧本 → 角色 → 场景 → 分镜 → 出图/导出**，可跳跃切换、反复迭代。
- **依赖提醒**：剧本/角色/场景任一变更后，下游镜头与其已生成图标记「待刷新」（stale）；重生成一律手动触发——烧钱操作不自动跑。
- 不做线性向导（资料明说创作是反复迭代：修镜头/换角色重出图），不做单页纵滚（一集 30+ 镜头信息量爆炸）。

### D4 端范围：桌面+平板+移动，响应式一套代码
- 一期即三端可用：共用一套组件，Tailwind 断点适配（桌面多栏 / 平板中栏 / 移动单栏 tab 堆叠）。
- 不做三套代码；关键操作（生图按钮、批量确认、镜头重roll、上传回传）三端行为一致。

### D5 剧本环节：多来源 + AI 拆解审核卡
- 剧本三来源：① AI 对话生成（工作台内聊天，先问题材/基调/集数再出剧本，复用 planner 的交互模式）② 粘贴外部剧本 ③ 手写。
- 剧本定稿后「一键拆解」：AI 按资料第 2 课要求产出结构化审核卡——剧情概括 / 事件链 / 主要冲突 / 人物关系 / 情绪点 / 可视化动作，逐项可编辑、人工确认后才进下游。
- 拆解同时产出**违审替换建议**（资料第 7 课）：高风险表达 → 中性可视化描述，保留剧情核心。
- 人工审核要点（资料原话内建为审核卡自检项）：情绪点是否准确、爽点是否抓住、人物关系是否正确、逻辑是否顺畅、是否把心理描写转成可见动作。

### D6 生图批量粒度：手动为主 + 整集批量
- 默认每个生图按钮手动点（角色设定图 / 场景图 / 单镜头四宫格）。
- 提供**整集批量**：一键排队生成当前集全部镜头四宫格，点击前弹窗预估张数与费用量级，确认才执行；失败不阻塞队列，逐镜头报状态。
- 每张图可单独重roll；角色/场景图同理。
- （注：因 D7 选定一张整四宫格，原「单镜头一键 4 帧」粒度不存在——单镜头批量即生成 1 张四宫格。）

### D7 四宫格方案：一张整图，修镜头 = 整张重roll
- 每镜头生成**一张 2×2 四宫格图**（prompt 内含四格各自的画面描述），更贴资料「四宫格参考图直接喂即梦图生视频」的原生用法，且天然同风格。
- 四格设计原则内建进 prompt 模板（资料第 5 课）：每格只放一个核心动作、场景位置明确、动作与情绪是钉点。
- 修镜头 = 编辑该镜头 prompt（含四格描述）后**整张重roll**——该方案下单镜头修补的最小粒度；「不重写整张四宫格」体现为不动其他镜头。
- 出图自检项内建（资料第 5 课）：角色有没有变脸、场景是不是同一空间、角色站位是否正确。

### D8 即梦导出：镜头卡快捷 + 整集导出包
- 镜头卡上：一键复制视频提示词 + 四宫格图片下载 + 「打开即梦」按钮（新开即梦 web 页）。
- 出图/导出 tab 提供**整集导出包**：markdown/表格（镜头号、景别、运镜、提示词、声音要求）+ 全部四宫格图片打包 zip，文件名按镜头号命名规范（与回传对应）。
- 视频提示词要点内建进模板（资料第 6 课）：每个画板独立可用、动作自然衔接、人物站位清楚、景别清楚、声音要求清楚；默认无背景音乐、保留环境音/动作声/对白声。

### D9 题材定位：题材中立，主角自由设定
- 短剧不绑定兄妹人设：新建时填「主角设定」自由文本（人数/身份/关系/外形），任何题材可做。
- 所有提示词模板题材中立；不复用 novel 的哥妹枚举。
- 理由：短剧面向短视频平台，题材光谱远宽于兄妹小说；与此前「策划对话兄妹硬编码清除」的修正方向一致。

### D10 成品回传：上传归档 + 卡内播放
- 镜头卡留「上传成品视频」入口（选文件上传，存 `dataDir/works/{id}/duanju/videos/`），上传后卡内直接播放。
- 支持整集连播检查镜头衔接——「生视频 → 修镜头」环节的判断依据。
- 导出包命名规范（镜头号）保证回传时对得上号。

## 三、数据模型草案（`shared/src/duanju.ts`，zod strict）

```
Work.mode = 'novel' | 'chat' | 'duanju'        // WorkSchema 扩展；mode='duanju' 时 novel settings 不消费
DuanjuProject {                                 // 存 dataDir/works/{id}/duanju/project.json
  script: { source: 'ai'|'pasted'|'manual', text, confirmed }
  reviewCards: { summary, eventChain, conflict, characterRelations,
                 emotionPoints, visualActions, riskReplacements[] }   // 审核卡，可编辑
  style: string                                 // 画风，默认'动漫风'，全局可改
  characters[]: { id, name, profile(身份/年龄/外观锁定描述),
                  sheetImages[](转存路径), refImageId?, updatedAt }
  scenes[]:      { id, name, spec(空间结构/光影/关键道具/色彩), images[], updatedAt }
  episodes[]:    { id, index, title, synopsis }
  shots[]:       { id, episodeId, index, 景别, 运镜, actionStart, actionEnd,
                   staging(站位), dialog, sound, gridPrompt, gridImage?,
                   finalVideo?, stale, updatedAt }
}
```
- 图片/视频均为 server 转存后的本地路径；stale 由上游实体 updatedAt 比对推导，写入时维护。
- 具体字段命名与嵌套在实施计划阶段定稿，本草案表达结构与关系。

## 四、架构约束（硬指标）

- client 新增 `features/duanju/`：按 tab 拆子目录（script/characters/scenes/storyboard/export），**单文件 ≤300 行、每目录 ≤8 文件**；三端共用组件。
- server 新增 duanju 路由（剧本/拆解/角色/场景/集/镜头 CRUD + 图片生成代理 + 文件上传）；生图代理 = 新 `services/image.ts`，风格对齐 `services/llm.ts`（无状态、错误分类码、密钥不进日志）。
- prompt 模板独立成库（拆解卡模板/角色图模板/场景图模板/四宫格模板/视频提示词模板），与 novel/chat 的 prompt 引擎并列，不互相纠缠。
- 图片生成返回的临时 URL **必须**在 server 端下载转存后再返回本地路径给前端。
- 批量生成在 client 侧排队（复用 generation store 的队列经验），server 不维护批量任务状态。

## 五、实施前必验的 spike（Phase 0）——已验证（2026-11-07）

1. **参考图参数：✓ 已打通（最终方案 Data URL）**。实测历程：裸 base64 与裸公网 URL（含 MiniMax 自家 OSS 回源）均被**静默忽略**（HTTP 200 但人物完全无关，多次视觉比对确认）；`subject_reference:[{type:'character', image_file:'data:image/png;base64,...'}]` 的 **Data URL 形式完美生效**（四项人物锚点全中）。官方 OpenAPI 规范亦确认支持 Data URL。角色一致性方案定为：角色设定图转存后，生四宫格时由 server 读本地文件转 Data URL 传入。注意 `type` 必须为 `character`（否则 2013）；官方提示参考图最佳为「单人正面照」→ 角色设定图 prompt 固定正面全身。
2. **生图 key：✓ 复用** `secrets.json` 的 `claude.apiKey`（与 LLM/TTS 同 key 同账号），无需新增配置。
3. 补充实测：URL 有效期 **24 小时**（转存为硬需求）；n≤9、prompt≤1500 字符；`aspect_ratio` 支持 1:1/16:9/4:3/3:2/2:3/3:4/9:16/21:9；每张生成约 15-17s；`image-01-live` 另有 style 画风对象（一期不依赖，prompt 驱动足够）。spike 脚本：`v3/scripts/spike-minimax-image.mjs`。
4. 移动端 webview 视频播放/上传兼容性：列入 Phase 4 验收项（需 APK 实测，不阻塞开发）。

## 七、实施切分建议（功能纵切，每期三端可用）

- **Phase 0**：三项 spike 验证（半天内）。
- **Phase 1**：WorkMode 扩展 + 新建入口（桌面/移动）+ 数据模型 + 工作台骨架 + 剧本 tab（多来源+拆解审核卡）。
- **Phase 2**：角色 tab + 场景 tab + 生图链路（image-01 代理、转存、重roll、参考图）。
- **Phase 3**：分镜 tab（按集拆镜头）+ 四宫格生成 + 整集批量 + 出图/导出 tab（镜头卡、即梦跳转、导出包）。
- **Phase 4**：成品回传 + 整集连播 + stale 依赖提醒完善 + 移动端打磨。
